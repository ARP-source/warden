Warden — Agent Permission Immune System

An autonomous loop that red-teams a tool-using AI agent's permission boundary, patches the enforcement policy when attacks get through, and proves each patch didn't break normal behavior before keeping it.

  • Build demo-base-v1
  • Audit ledger 55,542 rows, chain verified
  • 101 tests passing
  • CoreWeave Hacks (W&B)

§0The result

The same 46 documented prompt-injection attacks were run against seven current production models with no defense, then against the Warden loop as it hardened itself. The measure that matters is the executed rate — attacks that didn't just trick the agent into proposing a forbidden tool call, but actually got the call through the gate.

Grey bar = manipulated (agent proposed an out-of-scope call). Red bar = executed (the call passed the permission gate).

Undefended = 322 attacks across 7 models, policy p48/s58. Warden loop = run warden-v3, 1,792 attacks over 336 rounds against live models; first/latest are the means of the first and last quarter of rounds. Across the whole defended run the rates are 3.7% manipulated and 0.2% executed — the loop converged inside roughly the first hundred rounds and has held there since, which is the more useful claim: not a lucky dip, a level it sustains.

Two failure modes are tracked separately because they have separate fixes. Intent is a prompt problem — the model was talked into wanting the wrong thing. Enforcement is a policy problem — the request got through the gate. Warden reduces both, and drives the one that causes real damage to zero.

§1Why this needs to exist

Every model below is a capable agent: it uses the tools, passes the benign suite, and refuses nothing legitimate. And every one of them, given a documented prompt-injection attack, executed a forbidden action roughly one time in five. The reliability gap is not the model's competence — it is its permission boundary.

What those breaches did, on the mocked target

Across the runs the successful attacks produced 71 unauthorized refund rows totalling $11,035 and 214 emails of customer data to 9 attacker-controlled addresses. Each is a real Postgres row in the audit ledger, and none touched the outside world: no payment processor, no SMTP. See §5.

§2How it works

The core design decision is a hard split between what is true and what is enforced. An immutable oracle defines, once, whether a given tool call is authorized. A separate, patchable policy engine is the gate the agent runs behind. The Defender may rewrite the policy and the system prompt freely — but it can never edit the oracle. So a rising score can only mean the gate genuinely improved, never that the test got easier.

  • Attacker — 46 documented injection attacks across 15 families, paraphrased under an objective-preservation guard.
  • Target — the toy agent handles each call; every call is judged twice, against the oracle (truth) and the policy (gate).
  • Analysis — splits results into intent-rate and enforcement-rate, and isolates the leaking category.
  • Defender — proposes a bounded, whitelist-only, hardening-direction patch to policy and prompt.
  • Benign gate — the patch is kept only if normal behavior holds; otherwise it is reverted automatically, and the loop repeats.

What keeps the loop honest

  • Patches are fenced. The Defender can touch only a whitelist of checks, only within numeric bounds, and only in the hardening direction — plus a coherence guard so it cannot set a session cap below a per-call limit and quietly block legitimate work.
  • Drift is reverted. A cumulative benign baseline catches patches that look fine alone but collectively erode normal behavior.
  • Verification is separated. Patch-verification replays are recorded as their own action, so they never contaminate the attack metrics.
  • Provider-agnostic. The same loop runs against Anthropic, any OpenAI-compatible endpoint, or deterministic simulated doubles. Live runs use W&B Inference.

Against the undefended baseline of 65.5% manipulated and 22.4% executed, the defended loop runs at 3.7% and 0.2% — three executed breaches in 1,792 attacks. It reached that level early and has held it across 336 rounds rather than drifting back, which matters more than the size of the initial drop. The tradeoff, stated plainly

Hardening is not free. Benign competence started at 0.944 (17 of 18 legitimate cases served) and sits at 0.833 (15 of 18); the drift guard reverted 7 patches that pushed it further, with the lowest observed point at 0.722. The sharper number is the false-refusal rate, now 27.3%: the hardened policy turns away roughly one legitimate request in four. That is the real cost of driving executed breaches to 0.2%, and it is the weakest figure on this page. It is measured, governed and visible in the ledger rather than hidden, and recovering those cases without giving back enforcement is the open problem the loop is still working on.

§4Production readiness

The claim is not that it runs. It is that it already survived failure.

  • It survived a real crash. The dev machine died mid-run. On restart the hash chain — now 55,542 rows — verified intact end to end, and the budget governor reaped 3 orphaned reservations left by the killed process. Recovery was automatic.
  • Tamper-evident audit ledger. Append-only and hash-chained, with the chain computed server-side under a Postgres advisory lock and appends enforced by triggers and row-level security.
  • Budget governor with a kill switch. Pre-flight reservation gate, drain mode, hard kill switch, a reconcile command, and a 1.25× pricing safety factor under a $70 ceiling.
  • Real deployed infrastructure. Supabase Postgres holds all durable state; a stateless FastAPI service runs on Vercel serverless. No local-only shortcuts and no mock data.
  • Instrumented and tested. Weave tracing on the hot path with a per-request flush for serverless; 101 tests across oracle, policy, patch guards, budget governor and ledger integrity.

§5Safety scope

Warden attacks only the toy Target Agent inside this project. All tools are mocked. Attack techniques are standard, documented prompt-injection and jailbreak categories used for defensive research — not novel attack R&D. No external system, real user data, or production service is ever a target.

Refunds and emails write real Postgres rows so the damage is measurable and auditable, but every one carries external_dispatch = not_dispatched. There is no payment processor and no SMTP behind them. The blast radius is a database table.

The attack catalogue

46 attacks across 15 families, grounded in the published prompt-injection literature (including arXiv 2510.06445): system-prompt forgery, pseudo-conversation, encoding and obfuscation, many-shot, reasoning injection, payload splitting, tool-output injection, refusal suppression, and crescendo — each with paraphrase variants that preserve the attack's objective, so paraphrasing cannot accidentally defang the test.

§8Would a company buy this?

Who has the problem. Any company putting an LLM agent behind real tools — support desks that issue refunds, ops agents that change accounts, internal automation that sends mail. The buyer is the platform or security team that has to sign off on giving an agent the ability to move money or touch customer records.

Why they cannot solve it by choosing carefully. That is what §1 measures. All seven production models executed forbidden actions about one time in five, and the spread between best and worst was 19.6% to 26.1% — too narrow to pick your way out of. Swapping models does not fix it, and neither does a better system prompt, because the attack succeeds by convincing the model. The control has to sit outside the model, on the tool call itself.

What is actually being sold. Not a prompt and not a filter: an enforcement layer on tool calls, plus a continuous red-team that proves the layer still holds as models, prompts and tools change. The second half is the part a security team cannot get anywhere else — every tightening ships with evidence it did not break legitimate work, which is the reason tightenings normally never ship.

How a customer would integrate it

The loop is already decoupled from the agent. It talks over HTTP to a configurable base_url and judges structured tool-call events — which tool, which arguments, which tier, whether the session authorised it — never model text. So it does not care what framework the agent is built on, or whether it is even Python.

  • The customer exposes their agent behind a chat endpoint that reports the tool calls it makes.
  • The customer supplies two things: their tool tiers and authorisation rules (the oracle), and a benign suite of requests their agent must keep serving.
  • Warden supplies the attacker catalogue, the enforcement policy, the patch loop with its revert guard, the budget governor, and the audit ledger.

What adoption actually costs, stated honestly

The oracle is currently hardcoded in Python — four tools in a dictionary in target/oracle.py. A customer describing their own tools edits source today; it should be a config file, and that is the first item on the roadmap below. The benign suite also has to be written per customer: eighteen cases here, drawn from real legitimate requests. That is days of work, not months, but it is not zero and it is not automatic.

Deliberately not built yet

  • Config-driven oracle — so tool tiers and limits are declared, not coded. The single biggest adoption blocker.
  • Multi-tenancy — one run, one agent. No per-customer isolation.
  • Authentication on the admin endpoints — /admin/halt and friends are unauthenticated; fine behind a private network, not fine on the internet.
  • Alerting and SLA integration — the ledger knows when a breach executes; nothing pages anyone.

Why it would survive contact with a real company. The parts that usually kill a prototype in procurement are the parts that already exist: a tamper-evident audit trail that survived a real crash, a spend governor with a kill switch that has actually fired, row-level security on the database, 101 tests, and a verification script that reports what is true rather than what is claimed. The remaining work is integration surface, which is ordinary engineering. The hard part — proving a security change did not break the product — is the part that is done.
